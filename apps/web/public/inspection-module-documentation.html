Business Overview & Objectives

What This Module Does

The Inspection Module is the core workflow engine for vehicle assessment in the workshop. When a customer brings in a car (or a recovery team collects it), the system guides an inspector through a structured 6-step process — from receiving the vehicle, through detailed technical assessment, to delivering a professional PDF report. The entire journey is digitized, auditable, and AI-assisted.

Business Problems Solved

  • Eliminates paper-based inspection forms
  • Creates legal record of vehicle condition at check-in
  • Standardizes inspection quality across all inspectors
  • Links vehicle findings directly to vendor part quotes
  • Gives customers a transparent, professional report
  • AI reduces missed items and improves diagnostic accuracy

Key Business Outcomes

  • Faster inspection completion with AI guidance
  • Reduced disputes via photo-documented condition
  • Parts procurement triggered directly from findings
  • Workshop health scores for performance tracking
  • Customer approval workflow before work begins
  • Full audit trail from car-in to job completion

PART B
Inspection Workflow — 6 Steps
1

Step-by-Step Workflow

Each step is gated — the system enforces that previous steps are complete before unlocking the next one. The entire form state is continuously auto-saved to a draft_payload JSONB column in the database.

Step 1 — Collect Car  Gate / Reception

TriggerInspection created by Service Advisor from a customer lead (recovery pickup or walk-in)
Source Typesrecovery — car collected by recovery team  |  walkin — customer drove in
Source Media5 files uploaded at collection time: Front, Rear, Right, Left images + 360° Video
Inspector ActionCompare actual car vs. source media. Select "No difference" or "Yes — difference found" (with description). Mark complete.
Pre-inspection FormCustomer-reported issues (up to 5 questions: performance, sound/vibration, warning lights, fluid leaks, urgent priority) — shown read-only
Completion ConditionInspector explicitly marks "Collect Car Complete". Persisted as collectCarCompleted = true in draft_payload.
DB PersistenceSaved to inspections.draft_payload.collectCar — difference flag, note, reupload media, review logs

Step 2 — Start Inspection  Bay / Workshop

PurposeRecords the official inspection start timestamp — begins the audit trail for time-tracking
Unlock ConditionStep 1 must be marked complete
ActionInspector clicks "Start Inspection" button. System records startedAt timestamp.
DB PersistencePATCH inspections — sets started_at timestamp and status transitions begin

Step 3 — Checks & Notes  Visual Inspection

Part A: Media VerificationInspector reviews all 5 check-in media files. Each must be Verified or Rejected.
Rejection FlowSelect reject reason (Blur / Wrong angle / Not same car / Blocked view / Poor lighting), add note, upload replacement file. Old file is retained; replacement is linked.
Completion BlockerAny rejected media without a replacement upload blocks progression to Step 4
Part B: Issue NotesInspector adds damage/issue notes (description + photo). Unlimited entries. Saved as array in draft_payload.inspectionIssueEntries
DB PersistencePATCH inspections — draft_payload.carMediaReview, carMediaReplacement, carMediaRejectReason, carMediaRejectNote, inspectionIssueEntries

Step 4 — Vehicle Data & VIN  Data Entry

Required FieldsVIN (17 chars), Car Plate, Mileage (km), Front Tyre Size, Rear Tyre Size
VIN DecodeClick "Check VIN" → 17VIN API lookup → auto-fills Make, Model, Year. If multiple variants, dropdown shown for selection.
VIN Catalog LinkConfirmed VIN + EPC unlocks Parts Catalog in Step 5. The EPC (e.g. audi_vw) is stored and used for catalog API calls.
Tyre Options195/65R15, 205/55R16, 215/55R17, 225/45R17, 225/55R18, 235/55R19, 245/45R19 — custom saved values also preserved
Completion ConditionAll 5 required fields filled. System validates each field non-empty.
DB PersistencePATCH inspections — draft_payload.inspectionVin, inspectionPlate, inspectionMake, inspectionModel, inspectionYear, tyreSizeFront, tyreSizeRear, carInMileage

Step 5 — Inspection Findings & Parts  Core Work

The main step — divided into two sub-sections.

5A — Inspection Checks (Process Checks)
ChecksOil Check, Battery Check, Tyre Check, OBD Check
Status per CheckOK Issue N/A
Issue NoteIf "Issue" selected, a description textarea appears. Inspector describes the problem.
MediaMultiple photos can be uploaded per check (e.g. oil level dipstick, OBD screenshot). Stored as processCheckMediaMulti[key][]
5B — Findings / Parts Needed (Line Items)
Adding via CatalogClick "+ Add Line Item" → Parts Catalog modal opens → navigate Level 1-4 → check parts → "Add Selected Parts"
Adding ManuallyWhen no VIN catalog available: amber manual panel shows → select category, severity, observation, part name, part number, qty → "Add to Findings"
Severity LevelsSafety Risk Mandatory Recommended Optional
AI per PartAI generates 3–6 diagnostic questions per part. Inspector answers Yes/No/N/A. AI produces recommendation and description text.
Smart SuggestionsAfter each part added, AI suggests related components commonly found defective together (e.g. brake pads → suggest brake discs, fluid, sensor)
Completion ConditionAt least one saved line item. All saved items have part name and quantity.
DB PersistenceEach line item: INSERT into line_items table. AI fields saved in ai_questions, ai_answers, ai_recommendation JSONB columns.

Step 6 — Inspector Remarks & Report  Final Step

Inspector RemarksFree-text overall summary — vehicle condition, main concerns, priority recommendations
PDF ReportClick "Download Inspection Report (PDF)" → system generates PDF from inspection data → browser downloads file
Report ContentsWorkshop logo, vehicle info, customer details, all line items with severity, process check results, issue photos, health score, inspector remarks
Health ScoreAuto-calculated weighted score (0–100) using category weights: Brakes 16%, Engine 15%, Transmission 12%, etc.
Post-completionInspection becomes read-only (except for advisor to add estimate items). Status transitions to completed.

VIN & Parts Catalog Integration

17VIN API Integration

Integration with the 17VIN third-party API (api.17vin.com) for VIN decode and vehicle parts catalog. Authentication uses MD5-signed requests. File: apps/web/lib/vin17.ts.

Authentication & Request Signing

Every request to 17VIN is signed using an MD5 token computed over the request parameters. Credentials are loaded from environment variables.

// Environment variables required VIN17_BASE_URL=http://api.17vin.com:8080 VIN17_USERNAME=<workshop_username> VIN17_PASSWORD=<workshop_password> // Token generation (lib/vin17.ts) const token = md5Hex(usernameHash + passwordHash + urlParameter);

Parts Catalog Hierarchy (cata1 → cata4)

The catalog is a 2–4 level hierarchy. The system navigates it progressively — each level selection fetches the next level options.

LevelAPI ActionExampleParameters Required
cata1action=cata1Engine, Transmission, Brakes…vin, epc
cata2action=cata2Engine Block, Timing System…vin, epc, cata1
cata3action=cata3Timing Chain, Tensioner…vin, epc, cata1, cata2
cata4action=cata4Chain Set, Guide…vin, epc, cata1, cata2, cata3

When a node is marked isLast=true, clicking it calls action=part directly instead of fetching another level.

Synthetic Group Injection (Group Label Fix)

The action=part response never returns groups[] per part (a known 17VIN API limitation). Without groups, all line items would show "Unknown Group". The system solves this by injecting a synthetic group entry after each leaf selection.

// fetchPartsForLeaf() — inspection page.tsx const baseGroups = buildVinCatalogGroupOptions(normalizedParts); const syntheticGroup: VinCatalogGroupOption = { key: lastCataCode, // e.g. "ENG_123" label: groupLabel, // e.g. "Engine › Timing Chain" level: lastCataCodeLevel, }; setVinCatalogGroups([...baseGroups, syntheticGroup]);

The breadcrumb label is computed from selected node names at each level (e.g. "Engine › Timing › Chain Set") and passed through fetchPartsForLeaf(code, level, label).

PART G
Vendor & Part Quotes Flow
6

Vendor Integration

End-to-End Parts Procurement Flow

1. Inspector Adds Findings

Line items created during Step 5. Each has a part name, number, quantity, and severity.

2. Advisor Reviews & Approves

Service Advisor sets line item status from Pending → Approved. Items marked Rejected are dropped.

3. Part Inquiry Sent to Vendors

Approved items trigger inquiries to selected vendors. Vendors see the part name, number, and required quantity in their portal.

4. Vendor Submits Quote

Vendor opens the inquiry, confirms/edits the part number, uploads a part diagram photo, and fills in pricing for up to 4 types: OEM, OE, After Market, Used — each with brand, quantity, ETD, and delivery time.

5. Quote Validation

System validates: part number required, diagram required, each quote type with price must have a brand selected, at least one type submitted, no duplicate quote per vendor+line_item.

6. Advisor Selects Quote

Advisor compares quotes (OEM vs OE vs After Market vs Used). Selects approved_type. Line item order_status → Ordered.

7. Parts Received

When parts arrive, order_status → Received. Job card proceeds to workshop execution.

Draft Payload — Autosave Architecture

The entire inspection form state is serialized into a single draft_payload JSONB column on the inspections table. This enables full state recovery if the browser is closed or refreshed mid-inspection.
